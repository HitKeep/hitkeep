# Native human sessions

The fixed public clients are `hitkeep-ios` and `hitkeep-android`, with exact callbacks `https://hitkeep.com/auth/native/ios/callback` and `https://hitkeep.com/auth/native/android/callback`. A public client ID does not authenticate an installed binary. Release builds require OS verified HTTPS callback association and explicit consent for every attempt. iOS requires 17.4 or later; there is no private-scheme fallback. Android native passkey signing origins remain unconfigured until actual release certificates are approved.

This is a first-party continuation into the existing ordinary cookie session, independent of integration OAuth and AI enablement. It never upgrades an OAuth code/token, API client or embed credential. Current roles, permissions, plan limits and sensitive-operation checks still apply.

Use the optional `/api/status.native_auth` descriptor. Pin the selected canonical instance before opening the browser: lowercase scheme/host, remove HTTPS default port 443 and trailing slash, preserve the unescaped prefix and nondefault port. HTTPS port 80 remains a nondefault port. Credentials, query, fragment, escaped or ambiguous paths are invalid issuer configuration. Descriptor endpoints and callback `iss` use this same canonical issuer. Cloud region and self-hosted instance selection must never change during an attempt.

Literal prefix characters such as `!` remain literal in the canonical issuer. Requests may percent-encode those characters while retaining the descriptor's exact issuer; for example, a configured `/team!stats` prefix serves requests to `/team%21stats/api/status` with issuer `https://example.test/team!stats`.

1. POST `/api/auth/native/start` with bounded `application/json`: `client_id`, `redirect_uri`, `code_challenge` (43-character unpadded base64url SHA256), `code_challenge_method: "S256"`, `state` (16–512 printable ASCII characters generated randomly by the app), `intent: "login" | "signup"`, and optional `remember_me` (defaults false). Signup requires the selected instance's existing Cloud signup capability. Response: `{ "authorization_url": "…", "expires_at": "RFC3339" }`. Pending requests live for at most ten minutes.
2. Open the authorization URL in the system browser. GET `/api/auth/native/authorize?request=…` only continues existing login/signup/provider/MFA. The consent page shows the final signed-in identity, instance and full account authority. It fetches human-only `/api/auth/native/consent?request=…` to establish fresh transaction/browser-bound CSRF. Email verification in another browser resumes the same server-owned reference and actual authenticated subject; it never approves the app. Expired or missing native state requires restarting sign-in.
3. The explicit browser form POSTs `/api/auth/native/authorize` with exactly one `request`, `csrf_token`, `decision: approve | deny`, and optional `remember_me: true | false`. Strict same-origin Origin, current human cookie and browser binding are required. API/OAuth/embed bearer credentials are refused even with a cookie. The human-confirmed remember choice freezes here. Approval/denial is a single transition.
4. The exact claimed HTTPS callback contains only `code`, `state`, `iss`, or `error=access_denied`, `state`, `iss`. Code lifetime is at most one minute. The app validates the callback destination, saved state and issuer against its outstanding request. It never selects an endpoint from callback data.
5. POST the original instance's `/api/auth/native/exchange` with strict bounded JSON containing exactly `client_id`, `redirect_uri`, `code`, `code_verifier` (43–128 RFC7636 unreserved characters). No form submission, GET, ambient Authorization/API key, disallowed supplied Origin or null Origin. Native HTTP requests normally omit Origin. Success is `{ "status": "ok" }` plus fresh ordinary session and optional remember cookies directly in the native cookie jar; call unchanged `/api/user/bootstrap` next.

The server rechecks the current account, security state, issuer, client, exact callback and PKCE, then atomically consumes the code before issuing cookies. One concurrent exchange wins. Never retry a consumed code after losing the response or after issuance failure; restart. In-memory state is bounded and deliberately not durable across restart or leader change. It is never reconstructed from client fields. The server does not fetch callback URLs or relay self-hosted credentials through Cloud or the callback website.

Errors use bounded categories `invalid_request`, `invalid_grant`, `access_denied`, `temporarily_unavailable` and appropriate 400/403/503 status; existing authentication middleware/rate limits retain 401/429 behavior. Native API responses use no-store/no-referrer/frame protection. The exact consent/manage HTML documents use same-origin referrer policy so strict browser form Origin checks work; cross-origin callbacks receive no Referer. Other auth pages keep no-referrer. Requests, cookies, codes, verifiers and redirect locations must stay out of proxy logs and telemetry. Callback web delivery must have equivalent protections and no analytics/resources or credential relay.

Native jars and caches must be isolated by the **full canonical instance including prefix**: existing ordinary cookies retain `Path=/`. Logout clears cookies and removes the current remember token; it does not instantly revoke a copied stateless short JWT. There is no device inventory or new instant remote-revocation promise. Android native passkeys stay unavailable until verified signing origins exist; arbitrary self-hosted instances use browser passkeys. Cloud iOS passkeys additionally require the real RP associated-domain deployment and signed-device acceptance.

## Account deletion reauthentication

Native start optionally accepts `purpose: "account_delete"` together with `reauth_attempt`, only for `intent: "login"`. Both fields are required together; other purposes fail. Preparation uses the existing authenticated session; subsequent native start and exchange accept a fresh isolated app cookie jar without copying the original cookies. Possession of the attempt alone never proves authentication. The attempt freezes the existing account, canonical instance and consequences for at most ten minutes. The browser must complete an actual linked primary method and all applicable configured MFA even with existing HitKeep cookies. Approval identifies the account and explains that deletion still requires a separate final confirmation.

The callback and exchange fields remain unchanged. Only the successful one-use exchange binds deletion proof to the **new native session**, using its internal JWT JTI. Its intermediate browser session cannot perform or fulfill native deletion. Cookie restoration, session extension, signup, password recovery and consent alone never establish deletion proof. Old JWTs without JTI retain ordinary access and cannot fulfill fresh deletion proof. Clients must retain their original credential jar on cancellation and must never automatically delete after reauthentication.

Browser reauthentication uses the fixed server-owned `/settings?deletion_attempt=<opaque attempt>` as the login return. A deletion-purpose team OIDC callback applies configured local MFA and can redirect to `/login?returnUrl=<encoded return>#mfa_challenge=<existing opaque UUID>`. The page removes the fragment and POSTs strict JSON `{ "challenge_id": "<UUID>" }` to `/api/auth/mfa/resume`. This bounded, rate-limited, same-Origin operation requires its HttpOnly browser-binding cookie and returns only the existing MFA challenge/factors/passkey options. It issues no session or proof. Ordinary team SSO retains its existing policy.

Browser deletion reauthentication follows the configured HTTP or HTTPS instance, including its canonical prefix; native handoff remains HTTPS-only. Fragment cleanup preserves the server-owned login return through successful MFA. Changes to account email, credentials, configured factors or linked primary identities invalidate earlier deletion attempts, including already exchanged native proof, before subsequent response reads. Ordinary use of an existing linked identity does not invalidate proof.

Account removal clears pending provider continuations bound to that user. An earlier SSO state or verified social completion cannot recreate the removed account or sign into a replacement account with the same email. Newly started sign-in and signup continue to follow the instance's current policy.

## Native browser management

Ordinary customers can register a passkey, link a configured social provider, or connect Google Search Console for an exact manageable team through the system browser. These operations do not depend on AI configuration.

POST `/api/auth/native/management/start` with the current ordinary native session and strict JSON containing `client_id`, `redirect_uri`, `code_challenge`, `code_challenge_method: "S256"`, `state`, and one closed action:

- `action: "passkey_register"`, with no provider or team field. Enter the passkey name in the browser.
- `action: "social_link"` and `provider`, using a configured discovery provider ID; no team field.
- `action: "search_console_connect"` and `team_id`, using an exact currently manageable team UUID; no provider field.

No caller-supplied user, purpose, remember choice, arbitrary action, return URL, or dashboard destination is accepted. The server freezes the actual native session user and rechecks authority. Start returns the existing `authorization_url` and `expires_at`. Native start and completion may omit Origin and Referer; a supplied Origin must be the single exact canonical issuer origin. Ambient Authorization, API keys and embed authority are rejected.

The authorization URL forces fresh same-user primary authentication and all applicable MFA, then opens only `/auth/native/manage?request=<opaque>`. Existing browser cookies and email verification alone cannot approve an action. The page shows the instance, actual user, action, provider or team and requires an explicit same-origin CSRF-protected POST. It uses the existing passkey/provider/Search Console handlers in the browser's own cookie jar. A server-bound operation reference retains WebAuthn RP/verification, social state-cookie/nonce/PKCE, and Search Console original-user/team checks. One operation can win; only authoritative persistence records success. Its intended credential change preserves its own receipt while invalidating other attempts. A second browser decision POST returns the receipt to the existing exact iOS/Android HTTPS callback, containing only `code,state,iss`, or bounded `error,state,iss` for a denied known request.

POST the original saved issuer's `/api/auth/native/management/complete` using exactly the unchanged four-field `NativeAuthExchange` body and the current ordinary native session. Completion requires the frozen actual user, current authority, exact action/provider/team/client/callback/issuer, PKCE, expiry and committed success. It consumes once and returns only `{ "status": "ok" }`, with **no Set-Cookie**, session, deletion proof, API token or provider credential. Missing/expired sessions return401 without consuming the receipt; remember-only credentials never restore a session here. Extend or restore ordinary sessions through existing endpoints first. Login and deletion codes cannot complete management; management receipts cannot mint either kind of authority.

Discover this extension through optional `/api/status.native_auth.management`: `start_url`, `complete_url`, and `actions_supported`. Action support does not imply provider configuration or team permission. Save pending attempt kind locally; never accept a callback-supplied purpose. Validate destination, saved state and issuer, then recheck the app's saved instance/user/team and complete the receipt. Refresh `/api/user/security` or the exact team's existing Search Console status/properties after return. Cancellation, callback loss, receipt expiry/replay or lost success response never authorizes mutation retries; refresh can reveal a committed change. Search Console browser callbacks preserve the configured instance path prefix.
