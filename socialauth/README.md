# Optional Sign in with Apple

Apple joins the configured Google, GitHub and Microsoft providers in the existing login, invitation, signup and security settings flows. Browser, iOS and Android clients use the same system-browser flow and receive only HitKeep's session handoff. Apple configuration does not enable open signup: the existing managed Cloud signup switches, Terms, region and local MFA rules still apply.

Operators configure all three values in their deployment secret/configuration store:

- `HITKEEP_SOCIAL_APPLE_CLIENT_ID`: a registered Apple Services ID associated with a Sign in with Apple-enabled primary App ID.
- `HITKEEP_SOCIAL_APPLE_CLIENT_SECRET`: an externally generated, expiring Apple client-secret JWT. Rotate it before expiration using the same Services ID. HitKeep does not hold an Apple signing private key or create secrets at runtime.
- `HITKEEP_SOCIAL_APPLE_TOKEN_ENCRYPTION_KEY`: a stable, independently generated secret with at least 32 bytes. Retain it across JWT/session and Apple client-secret rotation and protect its backup. Replacing or losing it makes existing saved refresh tokens unavailable for automatic revocation; account deletion still proceeds with manual-revocation guidance.

Register the exact HTTPS public callback, including any configured instance prefix: `{HITKEEP_PUBLIC_URL}/api/auth/social/apple/callback`. Apple does not accept localhost or IP return URLs. Each installation needs its own correctly registered return URL and credentials; native clients never contain the client secret or encryption key. The configured audience is the Services ID, including for system-browser login from the official iOS and Android apps. This implementation does not accept a separate native Apple SDK grant or arbitrary caller-selected audiences.

The provider requests only `email`, uses code-only `response_mode=form_post` and `client_secret_post`, and validates RS256 JWKS signatures, issuer, audience, expiration and the saved nonce. Apple has no advertised PKCE support; the separate HitKeep native session handoff retains its S256 binding. A bounded, one-use server receipt bridges Apple's cross-site POST to a same-origin GET that still requires the original Lax state cookie. The POST never bypasses browser proof, sets a full session or grants deletion authority. Provider forms are bounded and never logged.

The immutable Apple subject resolves an already linked user before email policy. New automatic email matches and signup require a verified provider email. HitKeep accepts Apple's documented boolean and lowercase string verification values, keeps private relay addresses as supplied, and never guesses a hidden real address. Both current `private.icloud.com` and legacy `privaterelay.appleid.com` relay addresses use the normal generic email normalization. Repeated login needs no first-authorization `user` object. Linking a different existing HitKeep account remains an authenticated explicit operation; local MFA still runs before a login session is issued.

Register actual outgoing sender domains and addresses with Apple's private email relay and verify SPF/DKIM, envelope sender and From alignment. Test authorized signup, invitation, security, MFA and deletion mail delivery through the relay before enabling Apple for customers. A renewed Apple Developer membership alone does not establish Services ID, capability, callback, relay or signed-device readiness.

HitKeep discards access and ID tokens after validation and continues discarding all tokens for other social providers. For Apple only, it retains one authenticated encrypted refresh token, bound to the immutable subject and Services ID, on the social identity row. Public discovery, security summaries, API responses, audit logs and telemetry exclude that credential. A later refresh token replaces the previous one; an omitted refresh token preserves the existing value. This integration has no background refresh or retry service.

Unlink runs the existing serialized last-primary-method guard, attempts a bounded Apple grant revocation, then removes the local identity and encrypted credential. Apple unlink returns `200` with `{ "status": "unlinked", "provider_revocations": [{ "provider": "apple", "status": "revoked" }] }`, or `manual_revocation_required` when credentials are missing, configuration no longer matches, decryption fails, or Apple is unavailable. Other providers retain their existing `204` response. The dashboard shows a link to [Apple Account management](https://account.apple.com/account/manage) for manual revocation.

Account deletion uses `shared.NewAccountDeletionProviderRevoker` after fresh primary authentication and applicable MFA, approved billing cancellation and the persisted removal phase, before local credential cleanup. The deletion owner must wire this factory before startup removal recovery. Provider failure never blocks local account deletion and never reports a successful revocation; the account-deletion response carries the accurate provider outcome. There is no forced Apple password, new local password, durable retry queue or account-change webhook.

See Apple's [web configuration](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web), [token revocation API](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens), [TN3194](https://developer.apple.com/documentation/technotes/tn3194-handling-account-deletions-and-revoking-tokens-for-sign-in-with-apple), and [relay configuration](https://developer.apple.com/help/account/capabilities/configure-private-email-relay-service/). Source support is optional and disabled by default; it is not evidence of live App Store compliance or actual account registration.
